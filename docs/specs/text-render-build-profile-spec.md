# 文本渲染的构建档位与性能基线（Spec · 第二阶段）

- **状态**：`deferred` — 等 #53 全部落地后启动
- **前置**：#53（文本渲染控制台）
- **关联**：ADR 0013、`text-render-console-spec.md`
- **领域词汇基准**：`GLOSSARY.md`

---

## 问题陈述

#53 交付的是"什么都能切"。它必然引出一个问题：为了能切，是不是所有后端、所有依赖都得编进去？集成方只想要一套，能不能裁掉其余部分？

这个疑问实际混了三件事，必须拆开，否则会得出互相矛盾的结论：

| # | 问题 | 真正的约束 |
| :--- | :--- | :--- |
| Q1 | 运行期可切换，是不是意味着体积和开销都要翻倍 | 编译期裁剪 |
| Q2 | 切换时怎么保证不出错 | 缓存失效语义 |
| Q3 | 集成方选定方案后，其余方案不该编进去 | Cargo feature 设计 |

**核心判断：Q1 与 Q3 是同一个问题的两端，解法正交于 Q2。** 切换的可靠性属于正确性，与性能无关；性能问题落在体积和编译时间上，而不在帧率上。把三者混谈，就会得出"为了性能必须砍掉可切换性"这种错误结论——那等于为了省几十 KB 而放弃展台的验证能力。

---

## 一、代价分层：切换不花每帧的钱

| 开销类型 | 来源 | 是否随后端数量增长 | 由谁解决 |
| :--- | :--- | :--- | :--- |
| 每帧渲染 | 热路径上的一次分支 | **否**，永远只有一次 | 无需解决 |
| 常驻内存 / 二进制体积 | 编进来的后端及其依赖 | 是 | feature 裁剪 |
| 编译时间 | 同上 | 是 | feature 裁剪 |
| 切换瞬间 | 缓存重建 + 可能的重新布局 | 是 | 失效分级 |

单字形光栅化在几十微秒量级，一次 `match` 分支在纳秒量级，相差三到四个数量级。**把后端做成运行期可变，不会让每一帧变慢。**

所以"性能问题"的准确表述是：**集成方的二进制里不该同时躺着两套光栅化实现，以及它们各自的依赖树。** 这正是 feature 要解决的，而它不需要牺牲 #53 的任何能力——展台开全部后端，产品只开一个。

---

## 二、每帧的真实瓶颈不在后端选择

如果关心帧率，杠杆按收益排序：

1. **相位数量**。八相位意味着同一字形最多存 8 份位图，图集条目与上传量都是单相位的 8 倍。按 20×20 槽位、3500 个常用汉字估算（约 10400 个槽位/页，R8 每页 4 MiB）：

   | 相位档位 | 图集条目 | R8 页数 | 显存 |
   | :--- | :--- | :--- | :--- |
   | 8 | 28000 | 约 3 页 | 约 12 MiB |
   | 4 | 14000 | 约 2 页 | 约 8 MiB |
   | 1 | 3500 | 1 页 | 4 MiB |

   这是估算，假设单一字号、字形尺寸一致。真实项目混合字号会更多，但比例关系不变。

2. **缓存命中率与淘汰策略**。命中失败要重新光栅化并上传，一次上传的代价远高于一次虚调用。

3. **RGBA8 图集是否被白白创建**。当前 `GlyphAtlas::new` 无条件构造 `r8` 与 `rgba` 两张图集，即使整份 UI 里一个彩色 Emoji 都没有，RGBA8 的容量（每页 16 MiB）依然存在。**这是现在已经存在的浪费，与本 spec 无关但应在 Phase 2 一并处理**：改成按需创建，或在裁掉彩色 Emoji 的构建里直接不建。

结论：如果目标是性能，应当先看相位档位和图集策略，而不是先砍后端。**砍后端省的是体积，不是帧率。**

## 三、切换怎么才算"没毛病"

### 本质：切换不是换函数指针，是换一整份缓存

光栅化的产物进了字形缓存和图集。换后端等于让这份缓存全部作废。所以切换的成本 = 缓存规模 × 重建速度，与"换哪个后端"无关。

### 三条不变量

1. **只在帧边界生效。** 配置在帧内被读取时不得中途变化，否则同一帧的字形会来自两个后端，图集与顶点数据不自洽。#53 已经规定"每帧开始比对配置指纹"，这里补一条禁止项：任何 UI 事件都不得直接写入正在被渲染线程读取的设置。

2. **缓存键要么含后端标识，要么切换即全清。** 二者必居其一，不能都不做。#53 选的是后者（整表清空），理由是简单且省显存。但它有一个隐含限制：**同一进程里无法并存两个后端的字形**，任何"左右分屏对比 DW 与 swash"的需求都会撞墙。

   建议现在就在 `GlyphKey` 里预留一个后端标识位。成本是每条约 1 字节，收益是把这个选择留到将来：

   | 策略 | 显存峰值 | 切换成本 | 能否并排对比 |
   | :--- | :--- | :--- | :--- |
   | 切换即全清（#53 现状） | 一份 | 整表重建 | 否 |
   | 键含后端标识 | 两份（旧条目由 LRU 自然淘汰） | 懒失效，逐步替换 | 是 |

   预留字段不等于立刻采用第二种策略。**先把结构留出来，策略仍走全清**，等真要做对比模式时只改失效逻辑，不动键结构。

3. **报告区分"选择"与"生效"。** 已在 #53 中定义，此处不重复。补充一条：回退计数要在切换时归零，因为切换后的回退是新条件下的新事实，沿用旧计数会让"这次切换引入了回退"看不出来。

### 失效分级：哪一档会掉帧

| 档 | 影响面 | 包含项 | 切换代价 |
| :--- | :--- | :--- | :--- |
| L0 | 无 | 字体组（预览局部） | 无 |
| L1 | 塑形缓存 | 连字、双向、断行、字距、行高、塑形器 | 重排当前页文本 |
| L2 | 字形缓存 + 两张图集 | 光栅器、相位档位、Emoji 来源 / 呈现 / 光栅器、网格拟合 | 整表重建 |
| L3 | 渲染管线 | 距离场开关、混合空间、图层模式 | 重建 pipeline 与 bind group |

**只有 L1 存在掉帧风险**，因为它是全局设置：改一次会让所有页面的文本重新布局。L2 和 L3 虽然重建量更大，但只影响文本渲染本身，不触发整树 reflow，视觉上表现为"文本闪一下后稳定"。

这条结论可直接落到产品决策上：**运行期切换是开发者工具，不是产品功能。** 集成方若把 `TextRenderSettings` 直接暴露给最终用户，L1 那几项会造成明显的交互卡顿。产品应当在启动时定死配置，把设置面收进开发者面板或诊断入口。

## 四、编译期裁剪：feature 只能表达"启用集合"

Cargo feature 是加性的，无法表达"二选一"。所以不要设计 `backend = "swash" | "directwrite"` 这种互斥语义，只能设计成"启用哪些后端"，再由能力查询裁决。

### feature 设计

| feature | 作用 | 默认 |
| :--- | :--- | :--- |
| `backend-swash` | 启用 swash 光栅化（同时承担彩色 Emoji） | 由 `backend-native` 间接开启 |
| `backend-directwrite` | 启用 DirectWrite 光栅器（仅 Windows 生效） | 由 `backend-native` 间接开启 |
| `backend-native` | 意图型：平台最优，Windows→DW，其余→swash | **是** |
| `emoji-color-dw` | 彩色 Emoji 走 DirectWrite 层合成 | 否 |
| `sdf` | 距离场生成（EDT） | 由 `backend-native` 间接开启 |
| `text-console` | 展台参数面板，含运行期切换能力 | 否 |
| `text-backends-all` | 展台专用，一次性开启全部后端 | 否 |

要点：

- **`default` 只开 `backend-native`。** 若默认开全部后端，所有依赖方都被迫编译两份，feature 就失去意义。
- **`text-console` 是展台专属。** 产品不启用它，则 #53 的面板代码与切换逻辑整体不参与编译，"被抛弃的方案"连菜单都不会出现。
- 全部后端都关闭时用 `compile_error!` 给出明确提示，而不是让用户在运行期看到一个空能力表。

### 单后端构建下让分支真正消失

枚举变体本身用 `cfg` 声明，而不只是包一层 `if`：

```rust
pub enum RasterBackend {
    #[cfg(feature = "backend-swash")]
    Swash,
    #[cfg(all(feature = "backend-directwrite", windows))]
    DirectWrite,
}
```

单后端构建下枚举仅剩一个变体，`match` 塌缩为单一分支，分支判断被完全优化掉。这比"两个变体都在、运行期判空"更彻底，也是唯一能让"单后端构建没有切换开销"这句话成立的做法。

### 能力查询必须是三态

`TextCapabilities` 需要区分：

| 状态 | 含义 | UI 表现 |
| :--- | :--- | :--- |
| 可用 | 已编译且当前环境支持 | 可选 |
| 不可用 | 已编译但环境不满足（如字体缺表） | 灰化 + 环境原因 |
| 未编译 | 此构建未包含该能力 | 灰化 + "此构建未包含" |

第三态是新加的。不加它，用户看到"DirectWrite 不可用"会去翻系统设置，而真正原因是这个二进制根本没编进去。

### CI 矩阵

至少覆盖下列组合，每组都要编译通过并跑现有测试：

1. `default`（平台最优）
2. `--no-default-features --features backend-swash`（最小构建，验证无 Windows 依赖）
3. `--features text-backends-all,text-console`（展台构建，验证切换路径）
4. Windows 上 `--no-default-features --features backend-directwrite`（验证无 swash 依赖）
5. 全部关闭（断言 `compile_error!` 触发，用 `trybuild` 或构建脚本校验）

第 2 组和第 4 组是真正的验收点：它们证明依赖树确实被剪掉了，而不只是代码走了另一个分支。要断言 `cargo tree` 里不再出现 `swash` / `windows`。

## 五、一条关键联动：彩色 Emoji 是关掉 swash 的前提

这是前面几轮讨论中被忽略的一环。

只要彩色 Emoji 走 swash，`swash` 就必须编进来；`swash` 在依赖树里，`backend-swash` 就永远关不掉。**"DirectWrite 唯一后端"这个目标，卡在彩色 Emoji 上，而不在正文光栅化上。**

反过来，一旦 `emoji-color-dw` 完成，`backend-swash` 才能整体关闭，依赖树里 `swash`、`zeno` 一起消失。

这把"彩色 Emoji 走 DW"的性质改变了：它不再只是依赖收敛的洁癖，而是**体积裁剪的硬前提**。对一个 UI 框架来说，这个理由比"少一套代码"充分得多。

### 但有一个未验证的风险

关掉 `swash` 需要同时关闭 `cosmic-text` 的 `swash` feature。而 `cosmic-text` 内部是否在塑形、字体回退、字形度量等路径上依赖 swash，**尚未验证**。如果它用 swash 做度量，那关掉后塑形结果可能变化。

**Phase 2 的第一件事应该是做这项可行性验证**，一天之内可得结论，而不是先写彩色 DW 的四百行代码再发现路走不通。验证方法：临时关闭该 feature，编译 `unbound-text`，观察缺失符号集中在哪些模块，并跑一遍现有塑形测试看结果是否一致。

若验证结论是"关不掉"，则第五节的联动不成立，`backend-swash` 永远存在。此时彩色 DW 的价值回退为纯粹的依赖收敛，优先级应下调。

## 六、现在不做就会堵死的四件事

以下是 #53 实现期间必须遵守的约束。它们都极便宜，但错过了将来改动面很大。

1. **`GlyphKey` 预留后端标识位。** 现在加一个字段，成本可忽略；等所有缓存调用点铺开后再加，要改的地方是现在的数倍。策略仍维持"切换即全清"，只留结构不留行为。

2. **后端入口唯一。** 所有光栅化必须经过 `GlyphCache` 一处。若 #53 为了面板方便，在别处开了第二条光栅化路径，feature gate 就要改两处，且两处极易不同步。这是最容易在赶工时违反的一条。

3. **能力查询从一开始就是三态。** 若先写成 `bool`，后面加"未编译"这一态要改所有调用点。三态结构一次写对，`bool` 只是其中两态的退化。

4. **`windows` 依赖改 optional。** 这是**现在就存在的独立问题**，与 #53 无关，可以单独修：`unbound-text` 通过 workspace 继承 `windows` crate，一次性带入了 21 个 Win32 feature（Dwm、Gdi、Shell、Controls、IME、Registry…），而文本模块实际只需要 `Win32_Graphics_DirectWrite`、`Win32_Foundation`、`Win32_System_Com` 三项。其余是平台层的需求，因为 workspace 统一声明而被传染进了文本 crate。

   修法：`unbound-text` 不再继承 workspace 的 `windows`，改为自带一份最小 feature 集，并绑到 `backend-directwrite` 上。收益立竿见影，且不改变任何运行期行为。

## 七、现状数据（实测）

用于建立基线，口径为 debug 构建的 rlib（含元数据，不等于最终二进制的增量，仅作相对规模参考）：

| 依赖 | rlib 大小 | 说明 |
| :--- | :--- | :--- |
| `cosmic-text` | 17 MiB | 塑形与排版，必需 |
| `swash` | 13 MiB | 光栅化 + 彩色 Emoji |
| `windows` | 7.5–13 MiB（随 feature 集变化） | 当前含 21 个 Win32 feature |
| `zeno` | 416 KiB | swash 的扫描转换核心 |

`unbound-text` 依赖树共 70 个 crate，其中 18 个是字体 / 光栅化 / Windows 绑定相关。

这组数字说明：**`swash` 与 `windows` 是同一量级的重量级依赖**，任何"只留一个后端"的构建都能省下其中一份。具体省多少必须在 release 构建下用最终二进制体积衡量，debug 数据不能直接引用。

基线应在 Phase 2 建立并固定，至少包含：release 二进制体积、冷启动到首帧时间、连续切换 100 次的耗时、8 相位下渲染 3500 汉字的图集页数与显存峰值。

## 八、待决策清单

| # | 决策 | 选项 | 判断依据 |
| :--- | :--- | :--- | :--- |
| 1 | `default` 开什么 | 仅 `backend-native` / 全部后端 | 倾向仅 native：依赖方不该为展台的能力付体积 |
| 2 | 是否引入意图型 feature | 有 `backend-native` / 只有具体后端 | 倾向有：集成方描述意图比描述实现更稳定 |
| 3 | 缓存失效策略 | 全清 / 键含后端标识 | 现在选全清，预留字段；等出现并排对比需求再改 |
| 4 | 彩色 DW 优先级 | 受第五节联动影响 | 取决于 cosmic-text 关 swash 的可行性验证结果 |
| 5 | RGBA8 图集 | 无条件创建 / 按需创建 | 倾向按需：目前已存在无谓占用 |
| 6 | 体积预算 | 是否设硬上限 | 未定；建议先测出基线再定阈值，不要先拍数字 |
| 7 | 是否暴露给最终用户 | 仅开发者面板 / 产品可用 | 倾向仅开发者：L1 项会掉帧 |

## 九、验收标准

1. 五种 feature 组合在 CI 全部编译通过，测试全绿。
2. `--no-default-features --features backend-swash` 的构建产物中，`cargo tree` 不含 `windows`；`backend-directwrite` 单后端构建中不含 `swash` 与 `zeno`。
3. 全部后端关闭时构建失败，且错误信息明确指出需要至少一个后端。
4. 能力查询在未编译后端上返回"未编译"，与"环境不支持"可区分。
5. 连续切换 100 次后端，无字形串味、无图集泄漏、回退计数正确归零。
6. release 二进制体积、冷启动时间、图集显存峰值三项基线入库，后续变更可与基线对比。

---

## 范围之外

- **本轮不实现任何 feature gate。** 本文是决策依据与约束清单，不是实施单。
- **不做动态库拆分**（把后端做成 cdylib 运行时加载）。收益是单一二进制支持多后端，代价是 ABI 稳定与加载失败路径，与 UI 框架的分发形态不匹配。
- **不做构建期自动探测**（按系统版本自动决定编哪个后端）。构建应当可复现，探测放进运行期的能力查询。
