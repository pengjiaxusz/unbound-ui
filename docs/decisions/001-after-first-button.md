## 3. 现状增量（底座未覆盖、本次特有）

底座第 7 节已说明 Button 的形态与三个提交。这里补充与「下一步怎么走」直接相关的推导：

- 【事实】`ButtonDesc` 的源码注释明确写着「第二个控件只需要再写一个同样的描述符」，
  但当前**没有**共享的组件 trait / 注册机制 / 状态派生约定 / 发射产物结构；
  `ButtonArtifacts`、`ButtonTokens`、`ButtonVisualState` 都是 Button 专属类型。
- 【事实】`emit_button` 的产物同时包含图元、`HitRegion`、`A11yNode` 三类；
  这套「一次发射出三样东西」的模式目前只存在于 Button 内部。
- 【事实】状态色已占用颜色表 12–15 槽，`theme_table()` 仍是展台手写的 512 槽 `Vec<[u16; 4]>`，
  `unbound-theme` 声明了依赖但没有调用 `ThemeSet` / `ThemeLut`。
- 【事实】按需重绘的判定是 `visual != self.visual || click_count != rendered_clicks`；
  命中即 `rebuild()` 整场重建并 bump `generation`，`rebuild()` 内部还会重设 `Router` 的区域与语义焦点。
- 【事实】`apps/showcase/tests/gallery.rs` 已由提交 `4852108` 扩到 407 行、8 条断言，
  覆盖状态机、语义树、5 项几何体检与 hover/press 的离屏像素差异；
  `Harness::assert_clean` **只在测试里调用**，应用主循环没有运行时体检。
- 【推断】当前实现把「组件」定位成**应用内的一组纯函数 + 描述符**，而不是引擎层能力。
  依据：所有新类型都在 `apps/showcase/src/` 下，19 个 crate 里没有任何组件相关模块。

【未知】组件数量增加后全量 `rebuild()` 的实测开销、这套模式能否直接推广到有连续状态的控件
（Slider 的拖动值、Input 的光标与选区）、以及项目所有者对「组件层是否要独立成 crate」的倾向，
均未查到。请答复者把这几项标注为「不确定」，不要自行补齐。

## 4. 目标与最小验收定义

1. 第二个控件（任选 Toggle / Checkbox / Slider 之一）能接入展台并具备可点击或可拖动的可见反馈，
   且**不需要重写 Button 已有的状态派生与发射逻辑**（或重写范围有明确边界并可说明）。
2. `just check` 全绿、warnings 清零、`cargo fmt --check` 通过；`just test` 在无 Vulkan 设备的机器上自动跳过 GPU 用例且不失败。
3. 既有 8 条按钮断言全绿；新增控件的断言复用同一套 `Fixture` 模式，
   且至少一条不依赖 GPU 的 CPU 侧断言覆盖「事件序列 → 组件状态 → 发射产物」，不是只断言字符串或常量。
4. 主题切换的零图元上传仍成立（4 KiB 颜色表写入、0 次实例重传），slot 0 / 1 语义不变。
5. 状态跃迁时的上传量与场景规模的关系有实测数字或明确上限，并写进可复现的验证命令。
6. `--shot` 无头 PNG、既有离屏像素断言与窗口路径逐字节一致性断言继续通过。

## 5. 缺口链路

```
已落地：PlatformEvent → Router → ButtonVisualState::resolve → emit_button → 图元/热区/语义
                                      │
                        状态跃迁 → rebuild() 整场重建 → generation += 1 → 全量上传
                                      │
             缺：共享的组件骨架（状态派生 / 发射产物 / 注册 / 焦点顺序）
                                      ▼
             缺：第二个控件时「哪些代码能复用」的明确答案
                                      ▼
             缺：布局求解（现在仍是硬编码绝对坐标）
                                      ▼
             缺：组件数量增加后的重绘粒度与验证口径
```

具体断点：

- **复用边界不清**：`ButtonTokens` 把状态色与 `Palette` 解耦，但第二个控件是复制一份 `XxxTokens`，
  还是抽公共的 token 契约？`ButtonArtifacts` 是否该推广成通用发射产物？
- **布局**：`Gallery::build()` / `build_interactive()` 仍是 `x = 40 + index * 150` 式硬编码。
  控件一多，坐标冲突会先于架构问题暴露。
- **状态类型**：Button 的状态是离散枚举；Slider / Input 有连续值与文本缓冲，
  「交互瞬态从 `Router` 派生」这条原则能否覆盖，尚未验证。
- **验证**：CPU 侧 8 条断言已提交，但 `Harness::assert_clean` 只在测试里调用，
  主循环没有运行时体检；新增控件时这套夹具能否直接复用尚未验证。

## 6. 最纠结的三个张力点

1. **「零上传」叙事已经被改写**：现在只在相机 / 主题 / 同状态内移动成立，
   状态跃迁走整场 `rebuild()` + 全量上传（底座第 7.1 节）。控件数量从 1 变 10 后，
   这条路径与底座第 9 节「每帧成本与场景规模无关」的冲突会放大——是现在改，还是等第二个控件暴露再改。
2. **组件住在哪一层**：Button 在 `apps/showcase` 内，`ButtonDesc` 注释却承诺「第二个控件照抄即可」。
   留在应用里最省事，但 `app-guest` 的依赖护栏（底座第 3 节）意味着业务层将来拿不到这套组件；
   抽 crate 成本更高，却决定后续所有控件的位置。
3. **状态色槽位与主题表**：状态色直接占 12–15 槽，而 `theme_table()` 是手写的 512 槽表，
   `unbound-theme` 的 `ThemeLut` 没用上。继续线性占槽很快会变成「语义 token × 状态变体」的排列组合，
   现在收敛到主题系统、还是等第三个控件再说，是个早做早省的决策。
