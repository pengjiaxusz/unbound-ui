# WinUI 3 控件体系对齐、拼版像素差分与 Fluent 设计规律沉淀规格说明（Spec）

- **状态**：`ready-for-agent`
- **关联 ADR**：ADR 0007、ADR 0008
- **领域词汇基准**：`GLOSSARY.md`（后景、材质种类、来源、有效对比区、拼版图集、用例指纹、合成底板、基准对齐控件、自有独有控件）

---

## 问题陈述（Problem Statement）

当前用于复刻 Windows 11（WinUI 3）控件视觉与行为的对照系统存在五个阻碍全量推进的痛点：

1. **采集与渲染吞吐量极低**：官方参考截图宿主逐个用例切换控件并等待动画收敛（每个用例至少等待 350ms），本框架侧每渲染一个用例都重新创建并销毁一次 GPU 设备、离屏渲染器与字形图集。当对比维度扩展为「控件 × 状态 × 主题 × 后景」时，全量跑完一次耗时长达数十分钟。
2. **背景稀释导致假阳性通过（False Pass）**：参考截图画布尺寸过大，控件本体仅占画布不足 10% 的面积。差分器对整张画布统计色差均值与分位数，90% 以上完全一致的背景像素将控件局部的真实色差稀释了十余倍；同时直接将参考边界传入发射器掩盖了本框架控件自身固有尺寸（如默认高度 `36px` vs WinUI 标准 `32px`）的偏差。
3. **缺少跨次增量缓存**：即使系统版本、SDK 版本、用例规格或本框架控件源码未发生任何变化，每次运行仍会无条件重跑全部截图与渲染。
4. **缺少全量控件对标清单与命名对齐基准**：现有 109 个目录组件中混杂着 Web 风格命名（如 `Switch`、`Select`、`Modal`、`Alert`、`Collapsible`）、WinUI 3 标准控件与本框架专属的高级工作台组件，既看不出还缺失哪些 WinUI 3 控件，也未确立哪些属于本框架独有组件。
5. **自有独有控件缺少成体系的 Fluent 家族风格约束**：对于 WinUI 3 官方不存在的 43 个专业组件（如节点图、曲线编辑器、时间轴轨道、停靠面板），缺少将已验证的 WinUI 3 外观与交互规律迁移过去的机制。

---

## 解决方案（Solution）

构建一套从**权威清单 → 高吞吐精准检测 → 逐批对齐修复 → 规律技能沉淀 → 自有组件风格同化**的完整闭环：

1. **三合一控件清单与规范名对齐**：以 WinUI 3 官方名称为主键，将全部组件划分为**基准对齐控件**（52 个已实现 + 14 个 Community Toolkit 扩展）、**缺失待补控件**（18 个核心必补 P0/P1 + 6 个社区选补 P2）与**自有独有控件**（43 个），先在清单与差分目录中统一使用规范名，再以扩展—收缩方式分批完成代码标识符对齐。
2. **状态拼版图集采集与单实例离屏渲染**：参考宿主按「单控件 × 单主题 × 单后景」生成水平网格**拼版图集**（Contact Sheet），共享一次动画收敛与单次导出，再按控件边界加 `16 DIP` 出血边距切出紧凑单图；本框架侧在整個批量差分会话内全局复用单实例离屏渲染器。
3. **有效对比区（ROI）四重门禁**：差分器仅在 `union(reference_bbox, ours_bbox, controlBounds)` 外扩 `2px` 的**有效对比区**内统计色差，并同时校核：内容包围盒（`±1px`）、自由维度固有尺寸（`±1px`）、ROI 色差均值/p95（`≤ 1.5` / `≤ 4.0`）以及显著色差像素（`ΔE2000 > 5.0`）占比（`≤ 2%`）。
4. **双端用例指纹缓存与合成底板预留**：参考侧与本框架侧分别基于环境/规格与控件源码/调色板计算**用例指纹**，命中则跳过重截与重绘；同时在用例坐标中引入**合成底板**（`solid` 默认激活，预留 `mica`、`mica_alt`、`acrylic` 确定性底板纹理，待云母管线彻底完工后全量解锁）。
5. **Fluent 设计规律技能化与自有控件巡检**：在对齐基准控件并消除不一致后，将表面薄纱叠色、微描边高光、底边聚焦强调线、左侧选中胶囊条、圆角尺寸阶梯与弹簧动效提炼为 Agent 技能，并应用到全部 43 个**自有独有控件**上。

## 用户故事（User Stories）

1. 作为框架开发者，我希望参考截图宿主将同一控件的多个状态排入同一张**拼版图集**一次性等待动画收敛并切出紧凑单图，以便将参考图采集耗时缩短数倍。
2. 作为框架开发者，我希望本框架的批量差分器在单次运行中全局复用同一个 GPU 设备、离屏渲染器与字形图集实例，以便消除逐用例创建/销毁图形上下文的开销。
3. 作为框架开发者，我希望差分器仅在裁剪后的**有效对比区**内计算色差均值、分位数与显著色差像素占比，以便彻底杜绝大面积背景色稀释控件视觉差异导致的假阳性通过。
4. 作为框架开发者，我希望差分器同时校验控件在自由维度上的固有尺寸（如默认高度 `32px`），以便发现被外部传入矩形掩盖的默认尺寸偏差。
5. 作为框架开发者，我希望参考截图宿主与本框架渲染器都具备基于**用例指纹**的增量缓存能力（并提供 `--no-cache` 强制刷新开关），以便在未修改某控件规格或源码时毫秒级跳过重复工作。
6. 作为框架开发者，我希望在差分协议、截图宿主与主题查找表中预留**合成底板**维度（`solid`、`mica`、`mica_alt`、`acrylic`），以便在云母管线彻底完工后无需重构架构即可一键开启多材质乘积对比。
7. 作为框架维护者，我希望拥有一份以 WinUI 3 官方名称为主键的三合一控件清单，以便清晰掌握哪些已实现控件需要改名/归并、哪些 WinUI 3 控件尚待补齐、哪些属于本框架的**自有独有控件**。
8. 作为框架开发者，我希望将现有 Web 风格命名的已实现基准控件（如 `Switch`、`Select`、`Alert`、`Collapsible`、`Modal` 等）安全地对齐到 WinUI 3 官方规范名，以便 API 与官方生态心智模型一致。
9. 作为框架开发者，我希望分批把全部已实现的**基准对齐控件**及补齐的 18 个 WinUI 3 核心缺失控件接入批量像素差分闭环，并逐一修复它们与 WinUI 3 的视觉与尺寸不一致。
10. 作为框架设计者，我希望在解决完基准控件不一致后，将验证通过的 Fluent 视觉与交互规律沉淀为可复用的 Agent 技能，并据此巡检改造全部 43 个**自有独有控件**，以便本框架独有的专业工作台组件也具备纯正的 Windows 11 原生质感与交互一致性。

## 实现决策（Implementation Decisions）

- **单用例四维标识与元数据契约**：
  每个对比用例由 `(control, state, theme, backdrop)` 四元组唯一标识。默认 `backdrop = "solid"` 时文件基名保持 `<Control>_<state>_<theme>` 向后兼容；非 `solid` 时扩展为 `<Control>_<state>_<theme>_<backdrop>`。单用例元数据与汇总报告契约如下：
  ```json
  {
    "name": "Button_normal_light",
    "control": "Button",
    "state": "normal",
    "theme": "light",
    "backdrop": "solid",
    "fingerprint": "a1b2c3d4e5f60718",
    "explicitWidth": true,
    "roiBbox": [14, 14, 138, 50],
    "meanDe": 0.42,
    "p95De": 1.15,
    "overLimitRatio": 0.004,
    "intrinsic": [80.0, 32.0],
    "referenceSize": [120.0, 32.0],
    "intrinsicMatches": true,
    "cacheHit": false,
    "pass": true
  }
  ```
- **状态拼版分片与紧凑出血裁剪**：
  参考宿主以「单控件 × 单主题 × 单后景」为分片粒度构建水平网格拼版（每槽位 `260×96 DIP`），单次等待 ≥3 渲染帧且 `≥350ms` 让状态过渡动画完全收敛，单次导出整张拼版像素后，按每个槽位内控件的实际边界向外扩展 `16 DIP`（钳制在当前槽位边界内，防止相邻状态串扰）切出紧凑单图落盘。
- **有效对比区（ROI）四重门禁判定**：
  差分器从左上角基准像素提取双方内容包围盒 `reference_bbox` 与 `ours_bbox`，与 `controlBounds` 求并集后再向外扩展 `2px` 构成**有效对比区**。四重门禁必须全部满足才算 `pass`：
  1. `bbox_matches`：`reference_bbox` 与 `ours_bbox` 四条边误差均 `≤ 1px`；
  2. `intrinsic_matches`：高度误差 `≤ 1.0px`，且当 `!explicitWidth` 时宽度误差 `≤ 1.0px`；
  3. `roi_mean_de <= 1.5` 且 `roi_p95_de <= 4.0`；
  4. `over_limit_ratio <= 0.02`（有效对比区内 `ΔE2000 > 5.0` 的像素占比不超过 2%）。
- **双端指纹缓存计算规则**：
  - 参考侧指纹绑定：Windows App SDK 版本、操作系统版本、光栅化缩放、四维用例键与控件构造规格签名；
  - 本框架侧指纹绑定：四维用例键、画布尺寸、目标矩形，以及对应控件源码、基础图元源码与 Win11 调色板源码的内容哈希。
- **控件命名迁移采用扩展—收缩（Expand–Contract）模式**：
  由于目录枚举被全工作区的展台、无头测试与编译期穷举探针共同引用，重命名不得一次性硬改破坏编译；先在目录与公开导出中保留原名别名或映射表，分批迁移调用点后再收敛为 WinUI 3 规范名。
- **自有独有控件的规律同化机制**：
  自有独有控件不进入一对一参考图差分，而是通过 `fluent-control-design` 技能强制执行六项家族不变量：全语义令牌着色（零硬编码 RGB）、sRGB 薄纱线性反解、4px/8px 圆角阶梯、32px 标准交互高度与底边 2px 聚焦强调线、左侧 3×16px 选中胶囊条、以及 24 种控制状态组合下的图元数量恒定（Stable Shape）。

## 测试决策（Testing Decisions）

- **最高层测试接缝（Primary Testing Seam）**：
  整套特性优先复用并收敛到两个最高层外部行为接缝，不针对内部私有辅助函数写脆弱测试：
  1. **像素差分批处理与报告接缝**：给定一组参考 PNG + JSON 目录，运行批量差分器产出 `report.json`、本框架渲染图与带 ROI 框的热力图，断言四重门禁（ROI 抗背景稀释、固有高度拦截、超限像素占比拦截、二次运行缓存命中）。
  2. **组件目录穷举探针与 24 态形态恒定接缝**：对目录中的每一个组件（含对齐后的 WinUI 3 基准控件、新补齐的缺失控件与经 Fluent 规律改造的自有独有控件），遍历 24 种 `ControlState` 组合断言图元发射非空、图元数量恒定，并通过无头几何体检（无意外重叠、无越界溢出、无零尺寸）。
- **现有同类测试先例（Prior Art）**：
  - 色差与元数据解析测试：参考展台差分模块内既有的恒等色差、黑白极值色差与元数据解析单测；
  - 组件全目录 24 态形态恒定与健康度测试：参考组件库集成测试中的 `stable_shape`、`health` 以及各控件专属行为测试（如 `button_variants`、`checkbox_states`、`switch_spring`、`slider_keyboard_and_range`）。

## 范围之外（Out of Scope）

- **桌面窗口级实时 DWM 屏幕捕获门禁**：受桌面壁纸与多显示器位置影响，不纳入控件级自动化批处理门禁（由 ADR 0007 独立定义为人工屏幕捕获对照）。
- **云母后景管线本身的底层实现**：云母与自绘壁纸管线正在独立推进中；本 spec 负责在控件差分系统中预留好 `--backdrop` 维度与确定性合成底板，待云母完工后直接解锁全量矩阵。
- **非 Windows 11 风格主题（如 Material / Cupertino）的像素对齐**：像素差分仅针对默认 Windows 11 Fluent 主题集。
