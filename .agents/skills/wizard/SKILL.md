# 向导生成器（Wizard）

**向导（wizard）**是一个 bash 脚本，用来一步步引导人类完成那些手工做很繁琐、每次重新向 AI 解释一遍也很繁琐的人工流程。它会依次打开每个 URL、明确告知该点哪里/复制什么、采集输入值、写入对应位置（`.env`、GitHub secrets）、在每个阶段确认，并显示还剩多少阶段。它可以用来配置第三方服务、执行一次性迁移，或把项目从一个状态切到另一个状态。

顺滑的交互体验已经由 [template.sh](template.sh) 解决好了：分阶段进度展示、确认门禁、跨平台打开 URL（含 WSL）、密码隐藏输入、幂等的 `.env` 更新写入、`gh secret`/`gh variable` 写入以及收尾汇总。**你的工作只是梳理流程范围并编写各个阶段。** `STAGES` 标记之上的库代码在每个向导里都完全一致——这种一致性正是它的设计初衷：绝不要手改库代码。

向导默认是一次性的：为某次执行而建，保存在临时目录或 `scripts/` 下，事情办完就删掉。只有当用户希望在仓库里沉淀一条可重复执行的配置路径时才提交它。

## 流程

### 1. 界定流程范围

梳理出人类必须亲自做的每一步，以及沿途需要采集的每一个值。先读仓库，不要盲问：

- 若是环境初始化：读取 `.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置以及 `.github/workflows/*`（每一个 `secrets.*` / `vars.*` 引用都是向导必须产出的值）。
- 若是迁移或状态切换：理清当前状态、目标状态，以及两者之间不可逆的动作。

然后向用户展示有序的阶段清单以及每个阶段产出的值，并请用户确认：对方可能会增删或重排顺序。

**完成标准：** 每个阶段按顺序列出，且对于每个采集值你都明确了：(a) 人类从哪里拿到它，(b) 写入哪里（`.env`、GitHub secret、两者都要，或不写入——某些阶段只是纯动作），以及 (c) 它是否是敏感密钥（隐藏输入）还是公开值。

### 2. 映射每个阶段的操作路径

为每个阶段写出人类跟随的精确操作路径：打开哪个 URL、在页面上点什么、值显示在哪里、填入哪个变量（例如：“Dashboard → Developers → API keys → Reveal test key → 复制”）。如果你并不确定对方当前的 UI 布局或精确命令，如实说明并询问用户或查阅文档：绝不要编造可能根本不存在的步骤。

**完成标准：** 每个阶段都对应到连陌生人也能照着做完的具体操作指令。

### 3. 编写向导脚本

把 `template.sh` 复制到目标路径。把示例阶段替换成按依赖顺序排列的 `stage`（每个步骤一个）。使用库提供的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。将 `TOTAL_STAGES` 设为实际编写的阶段数。

守住模板设定的品质标准：先打开 URL 再向用户要值；敏感值一律用 `ask_secret`；所有持久化值用 `write_env`；只对 CI 真正需要的变量调用 `set_secret`；任何不可逆动作前先调用 `confirm`。每个 `stage` 都会清屏以便只展示当前步骤：每个阶段只聚焦一件事，免得用户需要看的信息滚出屏幕。不要改动标记之上的库代码。

### 4. 校验与交付

- 运行 `bash -n <script>`；如果环境装了 `shellcheck` 也跑一下。
- 执行 `chmod +x <script>`。
- **不要**自己端到端运行它：它会弹浏览器并阻塞等待人类输入。改为静态走查：第 1 步列出的每个值都已采集并写入了正确位置，且每个 `set_secret` 的名字与 CI 里的 `secrets.*` 引用完全一致。
- 告诉用户如何运行。如果这是一条可重复的配置路径，提交它并在 README 中附上链接，让下一个人直接跑脚本而不用再重新问一遍 AI。
