# 拆分为工单（To Tickets）

将一份计划、spec 或对话拆分为一组**工单（tickets）**：纵向的曳光弹切片，每张工单都明确声明**阻塞它**的前置工单。

issue tracker 与分诊标签词汇表应当已经提供给你；如果没有，请提示用户先运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话中已有的上下文工作。如果用户传入了引用参数（spec 路径、issue 编号或 URL），拉取并阅读其完整正文与评论。

### 2. 探索代码库（可选）

如果尚未探索过代码库，先了解当前代码状态。工单标题与描述应使用项目 `GLOSSARY.md` 领域词汇，并尊重所触及区域的 ADR。

留意可以提前重构（prefactor）让后续实现更顺畅的机会：“先把改动变容易，再做容易的改动。”

### 3. 起草垂直切片

把工作拆成**曳光弹（tracer bullet）**工单。

<vertical-slice-rules>

- 每个切片都要一条窄但**完整**地贯穿每一层（schema、API、UI、测试）：纵向切片，绝不是只切某一层的横向切片
- 完成一个切片后，它本身即可独立演示或验证
- 每个切片的体量应能放进单个全新上下文窗口中完成
- 任何前置重构（prefactoring）应放在最前面

</vertical-slice-rules>

为每张工单标出其**阻塞边（blocking edges）**：在它开工前必须先完成的其他工单。没有阻塞项的工单可以立即开工。

**大范围重构（Wide refactors）是垂直切片的例外。** **大范围重构**是指某个机械性改动（重命名列名、修改共享符号类型），其**爆炸半径**波及整个代码库，导致改一处就会打断成千上万个调用点，没有任何单个垂直切片能绿灯落地。不要硬把它塞进曳光弹；改用**扩展—收缩（expand–contract）**序列安排：先**扩展**：在旧形式旁边新增新形式，保证现有代码不坏；接着按爆炸半径分批迁移调用点（按包或按目录），每批各自建一张被扩展工单阻塞的工单，由于旧形式仍在，每批都能让 CI 保持绿灯；最后**收缩**：当不再有旧形式调用方时，在被所有迁移批次阻塞的工单里删掉旧形式。如果连分批都无法单独保持绿灯，仍保留此序列，但让它们共享同一条集成分支，并共同阻塞最后一张集成与验证工单，只在终点保证全绿。

### 4. 向用户核对拆分方案

以编号列表展示拟议的拆分方案。每张工单列出：

- **标题**：简短清晰的描述性名称
- **阻塞项（Blocked by）**：必须先完成的其他工单（若无则写无）
- **交付内容**：这张工单打通的端到端行为

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞关系是否准确：每张工单是不是只依赖了真正卡住它的前置工单？
- 有没有需要进一步合并或拆分的工单？

迭代调整，直到用户认可拆分方案。

### 5. 发布工单到已配置的 tracker

将认可后的工单发布出去。**发布方式**取决于 `/setup-matt-pocock-skills` 配置的 tracker；工单内容本身完全一样，只有阻塞边的表达形式不同：

- **本地文件** → 按依赖顺序（阻塞者在前）从 `01` 开始编号，在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张工单写一个独立文件。每个文件中的 `Blocked by` 列出它依赖的编号/标题。使用下方的本地工单模板：每张工单一个文件，绝不合并成单一文件。
- **真实 issue tracker（GitHub、Linear 等）** → 按依赖顺序（阻塞者在前）逐个创建 issue，使每张工单的阻塞边能引用真实编号。平台支持原生阻塞关系时优先使用原生关系；否则在工单的 `Blocked by` 中写明阻塞 issue。如果源头是一个已有 issue，将每张工单设为它的子 issue（按 tracker 文档操作）。除非另有指示，统一贴上 `ready-for-agent` 分诊标签——这些工单在设计上就是 Agent 可直接认领的。

按**前沿（frontier）**推进：所有阻塞者都已完成的工单即可认领。对于纯线性链条，就是从上到下依次推进。

**不要**关闭或修改任何父 issue。
