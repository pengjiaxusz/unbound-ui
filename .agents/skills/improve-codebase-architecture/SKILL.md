# 改进代码库架构（Improve Codebase Architecture）

挖掘架构摩擦点并提出**深化机会（deepening opportunities）**：把浅模块重构为深度模块，目标是提升可测试性与 AI 可导航性。

本命令以项目的领域模型为背景，并建立在共享的设计词汇表之上：

- 调用 Skill 工具执行 "codebase-design" 获取架构词汇表（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除测试、“接口即测试面”、“一个适配器 = 假想接缝，两个 = 真实接缝”）。在每条建议中严格使用这些术语，不要漂移成 "component"、"service"、"API" 或 "boundary"。
- `GLOSSARY.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应轻易推翻的既有决策。

## 流程

### 1. 探索

**扫描前先定范围：YAGNI。** 深化模块的价值在于让后续修改更容易，因此把权重放在最近频繁变动的代码区域。动手看代码前先决定*看哪里*：

- 如果用户指定了方向（某个模块、子系统或痛点），直接按该方向走，跳过下方推断。
- 否则，回溯一段较长的提交历史（`git log --oneline`），找出代码库的热点（反复被修改的文件与区域），让这些路径优先吸引你的注意。如果改动高度分散、没有明显热点，再扩大扫描范围。

先阅读项目的领域术语表（`GLOSSARY.md`）以及触及区域的所有 ADR。

接着拉起一个全新上下文窗口的 sub-agent 遍览代码库。不要套用死板规则，顺着探索过程中的真实摩擦感去记录：

- 理解一个概念时，需要在哪些地方在大量小模块之间反复横跳？
- 哪些地方的模块**过浅**，接口几乎和实现一样复杂？
- 哪些地方仅仅为了可测试性抽出了纯函数，但真正的 bug 全藏在它们如何被调用上（缺乏**局部性**）？
- 哪些紧耦合模块跨接缝发生了泄漏？
- 代码库中哪些部分没有测试，或者通过当前接口极难测试？

对任何疑似过浅的模块应用**删除测试（deletion test）**：如果删掉它，复杂度是会集中收拢，还是仅仅被搬走？“是的，会集中”正是你要找的信号。

### 2. 以 HTML 报告呈现候选方案

在操作系统临时目录下写入单个自包含 HTML 文件，不要让任何产物落入仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 下为 `%TEMP%`），写入 `<tmpdir>/architecture-review-<timestamp>.html` 以确保每次运行生成独立文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`）并告知绝对路径。

报告通过 **CDN 引入 Tailwind** 负责排版样式，通过 **CDN 引入 Mermaid** 绘制适合用图/流/时序表达的结构。将 Mermaid 与手写 CSS/SVG 混搭：依赖调用图、时序图等图状关系用 Mermaid；体量对比图、横截面、折叠态等更偏编辑排版的视觉用手工 `<div>`/SVG。每个候选都要有一张**改造前 / 改造后对比图**，尽量直观可视。

每个候选渲染一张卡片，包含：

- **涉及文件**：牵涉哪些文件/模块
- **问题**：为什么当前架构在制造摩擦
- **方案**：用平实语言说明要改什么
- **收益**：用局部性与杠杆解释，并说明测试会如何改善
- **改造前 / 改造后对比图**：并排自绘，直观展现“浅”与“深化”
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三选一，渲染为徽章

报告末尾附一个**首推建议（Top recommendation）**小节：你最建议先攻克哪一个候选、为什么。

**领域部分使用 `GLOSSARY.md` 词汇，架构部分使用 `/codebase-design` 词汇。** 如果 `GLOSSARY.md` 定义了 "Order"，就说“Order 接入模块”，不要说 "FooBarHandler"，也不要说 "Order service"。

**ADR 冲突**：仅当某个候选虽然与既有 ADR 矛盾、但摩擦大到确实值得重审该 ADR 时才展示出来，并在卡片中明确标注（例如警告框：_“与 ADR-0007 冲突，但值得重开讨论，因为……”_）。不要把 ADR 禁止的每一个理论重构都列出来。

完整的 HTML 骨架、图表模式与样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

此时**不要**提前给出具体接口设计。文件写好后，只向用户提问：“你想先探讨其中哪一个？”

### 3. 追问闭环（Grilling loop）

用户选定候选对象后，调用 Skill 工具执行 "grilling"，沿着决策树逐层追问：约束条件、依赖关系、深化后模块的形状、接缝背后放什么、哪些旧测试保留或替换。

随着决策逐渐清晰，就地同步维护领域模型，调用 Skill 工具执行 "domain-modeling"：

- **用了一个不在 `GLOSSARY.md` 中的概念来命名深化模块？** 把该术语补进 `GLOSSARY.md`（若文件不存在则懒创建）。
- **对话中把某个模糊术语打磨清晰了？** 当场更新 `GLOSSARY.md`。
- **用户以充分的承重理由否决了某个候选？** 提议记成一份 ADR，话术如：_“要我把它记成一份 ADR 吗？这样以后架构评审就不会再重复建议它了。”_ 仅当这个理由未来探路者确实需要知道以免踩坑时才提议；跳过临时性理由（“现在不值得做”）和不言自明的理由。
- **想为深化模块探索多套替代接口？** 调用 Skill 工具执行 "codebase-design"，使用其中的“设计两次（design-it-twice）”并行 sub-agent 模式。
