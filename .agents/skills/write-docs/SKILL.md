# 写文档

文档该怎么写，由项目决定，不由本技能决定。本技能的职责是：把项目已有的文档规则找出来并照办；找不到规则，就沿用老文档的实际写法；连可参考的文档都没有，才自由发挥。

## 立场

- **规则属于项目**：不带模板、不带固定章节骨架、不带字数上限、不带标签体系、不强制配图。
- **先找规则，再动笔**：多花两次检索，好过用自己的偏好覆盖项目既有惯例。
- **优先级**：目标文档或其目录自带的规范 > 项目约定文件 > 同批老文档的实际形态 > 自由发挥。
- **自成一体**：不预设任何上游流程或其它技能的存在，需要什么当场去查。

## 步骤

### 一、定目标

- 写哪个文件、新建还是更新。用户给了路径就用它；没给就从现有文档结构推断（同类文档放在哪、怎么命名），推断不出线索时才问一句。
- 更新已有文档时，先把整篇读完，弄清它现在的结构与口径，再动手改。

### 二、找规则（按顺序，命中即用）

1. 目标文档自身或其目录 README 里写着的规范段。不少项目会把「这些文档该怎么写」放在目录 README 末尾：分层、命名、禁止出现的内容、图的要求。
2. 约定文件：`AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` / 文档目录的 `README.md`，以及把格式固化成工具的配置（markdownlint、vale、dprint、prettier、文档模板、站点配置）。
3. 同批老文档的实际形态：抽 2~3 篇最近更新的，看它们的章节顺序与层级、单篇篇幅、语气（叙述还是电报）、语言（含双语或混排）、画不画图与画什么图、链接与引用写法、文件命名。

- 多套规则并存时按上面的顺序取值；规则之间打架，照更具体的那个（同目录优先于全局），并在交付时用一句话点明冲突，不擅自把别的文档一并改写。

### 三、写

- **有明确规则**：逐条照办——语言、命名、长度、结构、禁止项。规则与你的写作偏好冲突时，规则赢。
- **只有老文档**：把第二步提炼出的形态当规则用。新文档放进去要像同一批人写的；老文档没有的章节、图型、排版花样，不要引进。
- **什么都没有**：从读者与目的出发自己定——谁读、读完要能做什么、需要多少背景。只提四条要求：准确、可读、不注水、不编造。篇幅跟着内容走，既不凑也不砍。

### 四、交付前核对

- **事实**：每条论断都能落到代码、配置、命令输出或用户的明确说明上；属于推断的就写明是推断，或者先核实再写。
- **链接与路径**：引用的文件真实存在；引用的命令与选项拼写正确。
- **一致性**：同一概念与其它文档用同一个词，本篇内部不前后矛盾。
- **漂移**：发现老文档已经与现状不符时，只改与本次任务相关的部分，其余不一致点出来即可；除非用户要求，不做全篇重写。

## 常见坑

- **把偏好当规范**：默认「没有规范」，直到找到证据。
- **更新变成重写**：尽量保留原作者措辞与结构，把 diff 压到最小。
- **硬塞骨架**：老文档没有「概述 / 背景 / 总结」三件套，就别为了凑篇幅强加。
- **数字没有出处**：任何指标、预算、边界都要带上出处或测量条件。
- **新文档不进索引**：项目若维护索引或目录 README，按既有习惯登记新文档。
