本技能基于当前对话上下文与代码库理解产出一份 spec。**不要**再向用户提问追问；直接综合你已知的信息即可。

issue tracker 与分诊标签词汇表应当已经提供给你；如果没有，请提示用户先运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果尚未探索过代码库，先了解代码现状。整份 spec 统一使用项目 `GLOSSARY.md` 的领域词汇，并尊重所触及区域的 ADR。

2. 勾勒出你打算用来测试该特性的接缝（seams）。优先复用现有接缝而非新建；尽量使用最高层级的接缝；若确需新接缝，也尽量在最高层提出。全代码库范围的接缝越少越好——理想数量是一个。

与用户核对这些接缝是否符合他的预期。

3. 使用下方模板撰写 spec，然后发布到项目 issue tracker，并直接贴上 `ready-for-agent` 分诊标签（无需再额外走分诊）。

<spec-template>

## 问题陈述（Problem Statement）

从用户视角描述用户当前面临的问题。

## 解决方案（Solution）

从用户视角描述该问题的解决方案。

## 用户故事（User Stories）

一份详尽的编号用户故事列表，每条采用如下格式：

1. 作为 <角色>，我希望拥有 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行客户，我希望查看各账户余额，以便在消费时做出更明智的决策
</user-story-example>

这份用户故事列表应当非常全面，覆盖该特性的方方面面。

## 实现决策（Implementation Decisions）

已敲定的实现决策清单，可包括：

- 将要新建 / 修改的模块
- 这些模块将被修改的接口
- 开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互方式

**不要**写入具体文件路径或代码片段——它们很快就会过时。

例外：如果原型产出了某个比散文更精确地编码了某项决策的片段（状态机、reducer、schema、类型形态），将其内联到对应决策中并简要注明来自原型。只保留富含决策信息的核心部分，不要贴完整 demo，只留关键片段。

## 测试决策（Testing Decisions）

已敲定的测试决策清单，包括：

- 好测试的标准说明（只测外部行为，不测实现细节）
- 哪些模块将被测试
- 代码库中现有的同类测试先例（prior art）

## 范围之外（Out of Scope）

明确列出不在本次 spec 范围内的事项。

## 补充说明（Further Notes）

关于该特性的其他补充说明。

</spec-template>
