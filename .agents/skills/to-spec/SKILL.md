本技能基于当前对话上下文与代码库理解产出一份 spec。**不要**再向用户提问追问；直接综合你已知的信息即可。

issue tracker 与分诊标签词汇表应当已经提供给你；如果没有，请提示用户先运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果尚未探索过代码库，先了解代码现状。整份 spec 统一使用项目 `GLOSSARY.md` 的领域词汇，并尊重所触及区域的 ADR（特别是触及控件外观、溢出、浮层或动效时，必须遵循 ADR-0031 显式裁决**控件能力边界**）。

2. 勾勒出你打算用来测试该特性的接缝（seams）。优先复用现有接缝而非新建；尽量使用最高层级的接缝；若确需新接缝，也尽量在最高层提出。全代码库范围的接缝越少越好——理想数量是一个。

与用户核对这些接缝是否符合他的预期。

3. 使用下方模板撰写 spec（其中「能力边界裁决」为必选子项，不得留空或隐式略过），然后发布到项目 issue tracker，并直接贴上 `ready-for-agent` 分诊标签（无需再额外走分诊）。

## 问题陈述（Problem Statement）

从用户视角描述用户当前面临的问题。

## 解决方案（Solution）

从用户视角描述该问题的解决方案。

## 用户故事（User Stories）

一份详尽的编号用户故事列表，每条采用如下格式：

1. 作为 <角色>，我希望拥有 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行客户，我希望查看各账户余额，以便在消费时做出更明智的决策
</user-story-example>

这份用户故事列表应当非常全面，覆盖该特性的方方面面。

## 实现决策（Implementation Decisions）

已敲定的实现决策清单，可包括：

- 将要新建 / 修改的模块
- 这些模块将被修改的接口
- 开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互方式

**不要**写入具体文件路径或代码片段——它们很快就会过时。

例外：如果原型产出了某个比散文更精确地编码了某项决策的片段（状态机、reducer、schema、类型形态），将其内联到对应决策中并简要注明来自原型。只保留富含决策信息的核心部分，不要贴完整 demo，只留关键片段。

### 能力边界裁决（Capability Boundary Decisions，必选）

凡涉及控件、容器、浮层或动效的 spec，必须逐项给出明确裁决（不适用项须写明“不适用”及原因，不得省略）：

- **溢出策略（OverflowStrategy）**：裁决采用 `None`、`OverlayScrollbarVertical`、`OverlayScrollbarBoth`、`TabStripButtons`、`MenuOverflowPopup` 或 `ExternalScrollView`；若采用按需叠加滚动条，须明确未溢出零图元/零命中区与溢出态轨道/滑块交互契约。
- **文本截断与窄宽布局**：超长标签、标题或单元格文本的截断/换行策略。
- **空态表现**：空数据或零子项时的视觉与交互行为。
- **键盘导航与焦点策略**：焦点环、方向键、快捷键及 Esc 关闭/回退路径。
- **浮层贴边翻转**：弹出层、菜单或提示框贴近视口边缘时的翻转与夹紧规则。
- **动画中间帧几何不变量**：若存在驱动几何位置或尺寸变化的动画，写明过渡全程（任意中间帧）必须维持的几何连续性与零跳变约束。

## 测试决策（Testing Decisions）

已敲定的测试决策清单，包括：

- 好测试的标准说明（只测外部行为，不测实现细节）
- 哪些模块将被测试
- 代码库中现有的同类测试先例（prior art）
- 对应「能力边界裁决」的边界回归验证（如双态溢出契约测试、动画中间帧几何断言）

## 范围之外（Out of Scope）

明确列出不在本次 spec 范围内的事项。

## 补充说明（Further Notes）

关于该特性的其他补充说明。
