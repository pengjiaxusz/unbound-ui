# 提问工程与回答质量契约 (REFERENCE.md)

> 低频细节集中在此。`SKILL.md` 只保留工作流，本文件在写提问文件或校验回答时按需加载。

---

## 1. 为什么拆成两个文件

外部 Agent 看不到仓库、看不到本会话，且天然倾向于给出「全面而安全」的泛泛建议：
列一堆原则、给三种都可能对的方案、不敢下判断。材料的任务不是把资料堆过去，
而是**把回答空间收窄到能被执行**。

把项目全景和本次决策混在一份文件里，会有三个具体代价：

| 问题 | 后果 |
| :--- | :--- |
| 换一个决策就要重写整份项目介绍 | 每次征询成本极高，且容易把上次的事实口径写歪 |
| 项目介绍里夹着问题和验收 | 对方分不清「这是长期约束」还是「这是这次要选的」，会去回答背景而不是问题 |
| 章节号随内容重排 | 无法用「请重点看第 5 节」精确引导，只能让对方通读 |

拆成「稳定底座 + 一次性提问文件」后：底座只在项目事实变化时增量更新，提问文件永远短而锋利，
并且可以用稳定的章节号把对方的注意力钉在最相关的几节上。

**最有效的一招不是强调「请给高质量回答」，而是明确规定输出格式。**
格式会强迫对方做取舍、给第一步、给验收，空泛回答自然无处藏身。

## 2. 提问五维（每个待决策问题都要过一遍）

| 维度 | 要求 | 反例 → 正例 |
| :--- | :--- | :--- |
| **可判定** | 能回答「选 A 还是 B」 | 「组件层你怎么看？」→「组件层用函数式构建器 A，还是 `RawNodeDesc` + reducer B？」 |
| **有候选** | 给 2 至 3 个具体方案，不让对方从零发明 | 「该怎么设计？」→「A 无状态构建器 / B 数据驱动组件 / C 只写死一个样例」 |
| **有约束** | 写清评估维度，并指向底座对应章节 | 「哪个好？」→「按返工成本、是否违背底座第 9 节红线、加第二个组件的边际成本三项比较」 |
| **有验收** | 要求回答带「第一步改哪个文件 + 做完怎么验证」 | 「给个方向」→「明确指出第一步切在哪几个文件、各做什么、如何断言」 |
| **可执行** | 禁止只给原则 | 「保持高性能」→「每帧不产生堆分配；hover 不得触发全量重传」 |

规则：一份提问文件放 3 至 7 个问题。超过 8 个会分散焦点，对方会挑软柿子答。
把最纠结、最影响返工的问题放最前面。

**现状与推理要分开写**：如果工作树里已经有一份实现草稿，问题就不是「从零选架构」，
而是「评估这个已存在的实现是否采纳」。把草稿事实写进「现状增量」节，别让对方在真空里设计。

## 3. 输出契约（整段写进提问文件，不要改写）

```
请按以下格式回答，不要写成通用设计稿：

0. 对齐检查：用 3 至 5 条复述你理解的关键约束与目标；若理解有偏差，先指出再往下答。
1. 决策：对「待决策问题」一节中的每个问题给出「选 A / 选 B」的明确结论加一句话理由。「视情况而定」只能作为补充，不能作为结论。
2. 被否方案：每个问题列出被否掉的方案与具体否决原因。
3. 第一步：明确指出第一步切在哪几个文件、各做什么改动，以及这一步做完如何验证。
4. 分阶段计划：每阶段写「改动的文件或模块 / 交付物 / 可断言的验收 / 依赖的上一步」，不超过 4 个阶段。
5. 风险与回退：列出 2 至 3 个最可能翻车的点，以及各自的回退方式。
6. 待补充项：列出需要我方核实才能定论的信息，标注为「未知」，不要自行补齐。
7. 事实纪律：只使用项目简报与提问文件中出现过的类型、API 与文件路径；不确定就写「不确定」，不要编造名称或推测实现。
```

第 1 条里的章节号要与提问文件实际问题章节号一致（骨架 B 中是第 7 节）；
若骨架编号调整，两处必须同步改。

第 0 条「对齐检查」是性价比最高的一条：对方一旦复述错关键约束，后面所有建议都会跑偏，
而这一条能在第一段就把偏差暴露出来。

第 3 条「第一步」防止对方交付一份完整设计稿——设计稿看着很厉害，
但本地 agent 读完仍然不知道今天该改哪个文件。

## 4. 反幻觉条款（写进提问文件末尾）

```
给答复者的提示：如果不确定某个 API 是否存在，请直接写「不确定」，不必推测；
两份文件里的清单是从源码逐条核对过的，可作为可靠输入，但标注「文档自述，未复核」的数字
不要当作实测结论。我们更想要「第一步切哪里、以及为什么」的判断，而不是一份完整设计稿。
```

配套做法：底座里凡是从代码核对过的类型 / API / 路径，都附来源；文档自称的数据单独标注。
对方看到「这是核实过的」，才敢基于它下判断，而不是自己补一套想象中的 API。

## 5. 结构红线（`check_brief.py` 硬性项）

脚本接受两个路径：`python check_brief.py <项目简报> <提问文件>`，分三组校验。

### 5.1 项目简报（稳定底座）

1. 有【事实】标注
2. 有项目定位 / 规模章节
3. 有架构分层 / crate 地图章节，且列出足够多的 crate 名
4. 有一帧数据流章节
5. 有关键不变量章节，且覆盖 `generation`、排序键、颜色表、脏标记
6. 有已实现能力清单章节
7. 有组件层 / 缺口现状章节
8. 有稳定红线章节
9. 有测试 / 验收章节
10. 有关键文件索引章节
11. **不含**决策字段：待决策、一句话诉求、输出契约、「请按以下格式回答」
12. 有事实口径与答复纪律章节，含「不确定」与推测类措辞

### 5.2 提问文件

1. 开头写明「本次提交两个文件」，并给出阅读顺序
2. 引用 `PROJECT-BRIEF.md`，且按 `第 N 节` 指向底座章节
3. 有决策三要素（诉求 / 决定之后 / 怎样算成功）
4. 有「可直接复制的投递语」引用块，正文 ≥ 60 字且 ≤ 400 字
5. 有现状增量章节（本次特有事实，不复制底座）
6. 有目标 / 最小验收章节
7. 有待决策章节，编号问题 ≥ 3，且至少 3 个问题带候选方案标记
8. 有可能涉及的文件章节
9. 有输出契约或等价的输出格式要求
10. 有反幻觉提示（同时出现「不确定」与推测类措辞）
11. 无残留【填写指引】行、无依赖会话的指代词

### 5.3 联合项

1. 提问文件引用的每个底座章节号在底座里真实存在
2. 两文件都无敏感信息（后一项为警告）
3. 提问文件不过长（> 8000 字为警告：可能在复制底座内容）

## 6. 回答质量校验清单（回流时逐条打勾）

| # | 检查 | 不通过时 |
| --- | :--- | :--- |
| 1 | 复述了关键约束，且没有复述错 | 先纠正偏差再谈执行 |
| 2 | 每个待决策问题都有明确结论，没有「视情况而定」当结论 | 追问 |
| 3 | 给了被否方案与否决原因 | 追问，否则无法判断结论是否可靠 |
| 4 | 有「第一步改哪几个文件」 | 追问，这是本地 agent 最需要的一段 |
| 5 | 每阶段有可断言的验收 | 自行补验收，但标注为我方补充 |
| 6 | 建议引用的类型 / API / 路径都在两份文件里出现过 | 标为疑似臆造，先只读核对再采信 |
| 7 | 与底座【事实】无冲突 | 冲突项单独列出，不照抄 |
| 8 | 没有触碰红线，或明确说明为何红线可调整 | 默认不采纳 |
| 9 | 列出了「未知 / 待补充」项 | 转成只读探索任务 |
| 10 | 给了风险与回退 | 追问，或直接标注该方案未评估风险 |

**执行纪律**：校验不过就按第 7 节追问，不降级执行。
「先照着做、错了再改」在架构决策上代价极高，这正是引入外部判断要避免的事。

## 7. 追问模板（回答不合格时可复制）

```
你的回答里有几处还不足以让我们直接动手，请只针对下面几点补充，不要重写整份方案：

1. 第 X 个决策请明确选 A 还是 B，并给出被否方案的具体否决原因。
2. 请指出第一步具体改哪几个文件、各做什么改动，以及做完用什么断言验证。
3. 你提到的 <类型或 API> 不在两份文件里，请确认是已有的哪一个，或标注「不确定」。
4. 你的建议与项目简报第 X 节红线「……」存在冲突，请说明如何处理。

其余部分保持不变。
```

## 8. 反模式（明确禁止）

- 把项目底座写成某一次决策的简报（夹带诉求、问题、输出契约）
- 在提问文件里复制项目全景，而不是按章节号引用
- 每次征询都重写底座，或重排底座章节号导致历史提问文件引用失效
- 提问文件写成「帮我看看这个项目」式的开放问题
- 只堆事实、不给问题，或给了一堆问题却不给候选方案
- 把设计文档里「计划做」写成「已实现」，把注释里的控件名当成类型定义
- 忽略工作树里已有的草稿实现，让对方在真空里选架构
- 让对方一次产出完整组件库 / 系统设计稿
- 用「请给高质量回答」「请深入分析」代替输出格式契约
- 文件里出现「如上所述」「刚才那份」，对方根本看不到会话
- 只交付其中一个文件，或让用户自己去拼提问词
- 回流时不校验，直接把对方的每句话当指令执行

## 9. 从真实案例抽象出的要点

`docs/PROJECT-BRIEF.md` + `docs/decisions/001-after-first-button.md` 是本技能的首个实例：

- **底座**：30 秒速读、19+2 分层、一帧数据流、关键不变量表、按 crate 的已实现能力清单、
  组件层现状（含三个按钮提交与未提交测试快照）、稳定红线、测试手段、里程碑与未闭环项、
  文件索引、术语表。章节编号固定，全文【事实】/【推断】/【未知】分标，文档自称数据单独注明「未复核」。
- **提问文件**：开头写清「两个文件一起读」；第 2 节用表格精确指向底座第 3、5、6、7、8、9、10 节；
  第 3 节只写底座没有的推导与未验证点；第 6 节点出三个张力；第 7 节七个带候选的问题；第 9 节输出契约。
- **把文档冲突摆出来**：底座第 2 节点明 `README.md` 的原生 cargo 示例与 `AGENTS.md` 禁令冲突，
  第 11 节点明 `milestones.md` 与 `showcase.md` 关于 surface/swapchain 的描述不同步。
  不替对方抹平矛盾，反而能显著提高回答的可靠性。
- **主题切换只换提问文件**：写这份材料的过程中，第一个 Button 被三个提交完整接线，
  原先「怎么做第一个按钮」的提问立即失效。做法是**删除旧提问文件、新建一份新主题提问文件，
  底座只做事实增量更新、章节编号一行不改**。这正是双文件结构的价值。
