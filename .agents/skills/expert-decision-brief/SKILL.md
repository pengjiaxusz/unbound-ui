# 外部决策简报 (Expert Decision Brief)

产出**两个文件**交给用户，由用户一起发给外部 Agent：

1. `docs/PROJECT-BRIEF.md` —— **整个项目的稳定底座**，与具体决策无关，长期复用。
2. `docs/decisions/NNN-<topic>.md` —— **本次决策的提问文件**，每次征询新建一份。

**唯一质量标准：对方给回来的东西能不能直接指导本地 agent 动手。** 文件写得多漂亮都不算数。

## 快速开始

用户说「整理个文件我去问问别的 AI」时：锁定决策三要素 → 确认项目 brief 存在且未过期 →
按 [EXAMPLES.md](EXAMPLES.md) 的骨架 B 写一份新提问文件 →
运行 `python .agents/skills/expert-decision-brief/check_brief.py docs/PROJECT-BRIEF.md <提问文件路径>` →
用 present_files **一次呈现两个文件**，提醒用户把两个文件一起发出去。

## 两个文件的分工（不可混淆）

| | `PROJECT-BRIEF.md` | `questions` 提问文件 |
| :--- | :--- | :--- |
| 范围 | 整个项目：定位、分层、数据流、不变量、能力清单、红线、测试、索引 | 只写这一次决策 |
| 生命周期 | 稳定，事实变化时才增量更新；**章节编号是契约，不许重排** | 一次性，每次征询新建 |
| 含待决策问题 | **禁止** | 必须有 3–7 个 |
| 含验收 / 输出契约 | **禁止** | 必须有 |
| 引用关系 | 独立可读 | 按 `第 N 节` 引用底座，不复制底座内容 |

拆开的目的：换一个决策时不必重写项目全景，外部 Agent 也不会把「项目介绍」和「这次要回答什么」混在一起。

## 工作流

### 1. 锁定决策（先想清楚，别急着写）

明确三件事，缺哪项就用一句话向用户确认，不要靠猜：

1. **要对方决定什么** —— 一句话诉求，必须能回答「选 A 还是 B」
2. **决定之后做什么** —— 本地 agent 下一步的具体动作
3. **怎样算成功** —— 可断言的验收标准

把这三句原样写进提问文件第 1 节。用户只说「问问意见」时，先把诉求补成可判定形式。

### 2. 维护项目底座（通常是「校验」而不是「重写」）

- **不存在**：全仓只读盘点后按 [EXAMPLES.md](EXAMPLES.md) 骨架 A 生成。
- **已存在**：做一次**时效性核对**——工作树是否有新 crate / 新依赖 / 红线变化 / 里程碑闭环 /
  应用结构变化 / 未提交的关键改动。只增量更新变化处，**保留既有章节编号**，因为提问文件按编号引用它。
  没有变化就一个字都不改，并在回复里说明「底座未变」。

全仓盘点用 Explore 子代理、Grep、Read 逐条核对，禁止凭印象。全文统一打标：
【事实】已核实 /【推断】附依据的推理 /【未知】未查到。每条事实给来源（路径加行号或符号名）。
文档自称「已落地 / 已实现 / 已测」不等于代码里有，必须区分标注。

三项反幻觉核查（必做）：设计文档里「计划做 / 未来」不能写成「已实现」；注释或测试字面量里的类型名
不等于类型定义；依赖清单声明了某个包不等于代码真的调用了它。

外发前剔除密钥、token、私钥、个人信息、内部 URL，必要时脱敏。

### 3. 写本次提问文件

按 [EXAMPLES.md](EXAMPLES.md) 骨架 B 填充，提问规则与输出契约见 [REFERENCE.md](REFERENCE.md)。
路径 `docs/decisions/NNN-<topic>.md`，编号取现有最大值加一；**永远新建，不覆盖旧提问文件**。

开头写明「本次提交两个文件」与阅读顺序。正文只放底座里没有的东西：本次决策三要素、
引用底座哪几节、现状增量、最小验收、缺口链路、张力点、待决策问题、可能涉及的文件、输出契约。

### 4. 双文件自检

运行 `python .agents/skills/expert-decision-brief/check_brief.py <项目简报> <提问文件>`（只读）。
硬性项失败则补齐后重跑；警告项逐条判断。脚本会同时校验两文件各自的红线，以及
「提问文件引用的底座章节号真实存在」这一联合项。硬性项清单见 [REFERENCE.md](REFERENCE.md)。

### 5. 交付

用 present_files **一次呈现两个文件**（底座在前、提问文件在后）。回复里给出：

- 两个绝对路径加各自一句话概要，并明确「把这两个文件一起发给外部 Agent」；
- 本次最值得对方回答的 2–3 个**张力点**（把真正的两难点出来，是提高回答质量最有效的一招）；
- 底座本次是否更新过；没更新就直接说明。

提问文件第 0 节的投递语已经写好，用户可以直接连同两个文件一起贴过去。

### 6. 回流（用户带回回答时）

按 [REFERENCE.md](REFERENCE.md) 的「回答质量校验清单」**先校验再执行**：

1. 核对对方是否复述关键约束、是否区分事实与推测、是否标注不确定
2. 逐条比对建议与两份文件的【事实】和红线，冲突的明确标出，不照抄
3. 把「不确定 / 需补充」项转成只读探索任务，不当作已定结论
4. 拆成可执行步骤：具体文件、具体改动、可断言的验收；3 步以上用 TaskCreate 建任务
5. 回答不合格（空泛、无第一步、无验收、臆造 API）时按「追问模板」生成一轮针对性追问，不降级执行

## 边界

- 不替对方做决策，不把预设结论藏进提问文件
- 不自动发送文件；投递由用户手动完成
- 不把本次决策的问题、验收、输出契约写进项目底座
- 不在提问文件里复制底座内容，只按章节号引用
- 不写「如上所述」「刚才那份」「我们之前讨论的」等依赖会话的指代

## 关键原则

- 底座的价值等于「让对方少猜多少」，提问文件的价值等于「让对方少绕多少弯」，都不等于篇幅
- 每个问题都要能被回答成「选 A 或 B，因为 X，第一步改 Y 文件，验收是 Z」
- **索要输出格式比索要结论更重要**，明确格式能挡掉大部分空泛回答
- 回答回来先校验再执行；校验不过就追问
