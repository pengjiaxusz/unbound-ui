# 分诊（Triage）

推动项目 issue tracker 上的 issue 流经一个轻量的分诊角色状态机。

如果本仓库把外部 Pull Request 也作为请求入口（见 issue-tracker 配置），分诊同样覆盖它们：**PR 就是附带了代码的 issue**，使用相同的角色、状态与状态机，仅在下方标明“针对 PR”的几处存在细微差异。按 tracker 配置将裸写的 `#42` 解析为 issue 或 PR。

分诊期间发布到 issue tracker 的每一条评论或 issue **必须**以如下免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写持久有效的 Agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的运作方式

## 角色

两个**分类（category）**角色：

- `bug`：某处功能坏掉了
- `enhancement`：新特性或改进

五个**状态（state）**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待提交者补充更多信息
- `ready-for-agent`：规格已明确，可交由 AFK Agent 执行
- `ready-for-human`：需要人类亲自实现
- `wontfix`：不予处理 / 关闭

对于 PR，相同状态结合所附代码理解：`ready-for-agent` 表示已附上简报、应由 Agent 接手处理 diff 的下一步；`ready-for-human` 表示已就绪、等待人类合并。

每个已完成分诊的 issue 都应恰好带有一个分类角色和一个状态角色。如果状态角色互相冲突，先标出冲突并询问维护者，再做其他操作。

以上是规范角色名；tracker 中实际使用的标签字符串可能不同，映射表应当已经提供给你。若没有，请提示用户先运行 `/setup-matt-pocock-skills`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`；随后流向 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。当提交者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以手动覆盖；遇到看起来反常的状态跃迁时先标出并确认再执行。

## 调用方式

维护者调用 `/triage` 并用自然语言说明需求，你解析意图并执行。示例：

- “给我看看有哪些需要我关注”
- “一起看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些已经准备好让 Agent 领走了？”

## 展示待关注事项

查询 issue tracker 并按从旧到新展示三个桶：

1. **未打标签（Unlabeled）**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **自上次分诊笔记以来有提交者新动态的 `needs-info`**：需要重新评估。

当 PR 纳入范围时，把外部 PR 一并列入这三个桶，并在每行标上 `[PR]` 或 `[issue]`。发现列表只浮出*外部* PR（tracker 配置定义了谁算外部人员），因此协作者自己进行中的 PR 不算分诊工作。此过滤仅用于发现列表；点名指定的 PR 无论作者是谁一律正常分诊。

展示数量与每条的一句话摘要，由维护者挑选。

## 分诊单个 issue 或 PR

1. **收集上下文。** 通读完整 issue 或 PR（正文、评论、标签、作者、日期；若是 PR 还要看 diff）。解析之前的分诊笔记以免重复问已解决的问题。用项目领域术语表探索代码库，尊重相关区域的 ADR。对照代码库做两项检查：(a) **冗余检查**：按领域概念（不要只按请求字面词）搜索是否已存在该行为的现有实现，并汇报你查了哪里。若已存在，它属于“已实现”的 `wontfix`（第 5 步）；(b) **历史拒绝检查**：读取 `.out-of-scope/*.md`，提示任何与当前请求相似的条目。

2. **给出建议。** 向维护者说明你建议的分类与状态及理由，并附上与请求相关的代码库简述（含是否已实现），然后等待指示。

3. **核实声明。** 在进入任何追问之前，先核实原帖所说是否成立。对于 bug，按提交者的步骤复现；对于 PR，确认 diff 是否真能做到它声称的事——检出分支，跑相关测试或命令。汇报核实结果：已确认（附上代码路径）、未复现/失败，或信息不足（强烈指向 `needs-info` 的信号）。经过确认的核实能写出质量高得多的 Agent 简报。

4. **追问（如有需要）。** 如果请求还需要充实细节，先后调用两次 Skill 工具（`"grilling"` 与 `"domain-modeling"`），一轮一轮提问打磨清楚，随着决策落定同步打磨领域术语并就地更新 `GLOSSARY.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发表一条 Agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：采用与 Agent 简报相同的结构，但注明为什么不能委派给 Agent（需要主观判断、外部权限、设计拍板、手工测试）。
   - `needs-info`：发表分诊笔记（见下方模板）。
   - `wontfix`：关闭 issue，关闭评论取决于*原因*：
     - **已实现**：该功能在代码库中已存在。指明它所在位置；**不要**写入 `.out-of-scope/`（那个知识库只记录*被拒绝*的请求，不记录已建成的功能）。
     - **已拒绝（bug）**：礼貌解释原因后关闭。
     - **已拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中附上链接后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：贴上对应角色；若有阶段性进展可附可选评论。

## 快速状态覆盖

如果维护者说“把 #42 移到 ready-for-agent”，信任他的判断并直接应用该角色。先确认你即将执行的动作（角色变更、评论、关闭），然后执行，跳过追问。如果未经过追问就直接移到 `ready-for-agent`，询问是否需要顺便撰写一份 Agent 简报。

## Needs-info 模板

```markdown
## 分诊笔记（Triage Notes）

**目前已确认：**

- 要点 1
- 要点 2

**仍需你补充（@reporter）：**

- 问题 1
- 问题 2
```

把追问阶段已解决的所有结论收进“目前已确认”，避免工作白费。问题必须具体、可回答，不要写“请提供更多信息”。

## 恢复上次会话

如果该 issue 或 PR 上已经存在历史分诊笔记，先阅读它们，检查提交者是否已回答未决问题，先呈现最新状态全貌再继续，不要重复问已经解决的问题。
