# 领域建模（Domain Modeling）

在设计过程中主动构建并打磨项目的领域模型。这是一项*主动*纪律：质疑含糊用词、构造边界场景，并在概念结晶的那一刻立刻写进术语表和决策记录。（仅仅为了查阅词汇而*读取* `GLOSSARY.md` 不算本技能：那是任何技能都可以随手做的一行习惯。本技能用于你在*修改*模型的时候，而不是仅仅消费它。）

## 文件结构

绝大多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明仓库包含多个上下文，地图会指向各自所在位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级全局决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

懒创建文件：只在真有内容要写时才创建。如果没有 `GLOSSARY.md`，在第一个术语落定时创建；如果没有 `docs/adr/`，在需要第一份 ADR 时创建。

## 会话中的动作

### 对照术语表提出质疑

当用户使用的术语与 `GLOSSARY.md` 现有语言冲突时，立刻指出来：“你的术语表把 'cancellation' 定义为 X，但你刚才说的似乎是 Y。到底是哪一个？”

### 打磨模糊语言

当用户使用含糊或过载的词汇时，提议一个精确的规范术语：“你一直在说 'account'：你指的是 Customer 还是 User？这是两回事。”

### 讨论具体场景

当讨论领域关系时，用具体场景去压力测试它们。构造能探测边界情况的场景，倒逼用户把概念之间的界线说清楚。

### 与代码交叉核对

当用户陈述某件事如何运作时，检查代码是否一致。一旦发现矛盾就摆出来：“你的代码只能取消整张 Order，但你刚才说支持部分取消。以哪个为准？”

### 就地更新 GLOSSARY.md

只要一个术语敲定，当场更新 `GLOSSARY.md`，不要攒到最后一起写。格式见 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)。

`GLOSSARY.md` 应完全剥离实现细节。不要把 `GLOSSARY.md` 当成 spec、草稿本或实现决策仓库。它只是术语表，仅此而已。

### 审慎提议 ADR

只有当以下三条全部成立时，才提议创建 ADR：

1. **难以逆转**：日后改变主意的成本可观
2. **缺少上下文会令人困惑**：未来读者会纳闷“为什么当初要这么做？”
3. **真实权衡的结果**：存在像样的备选方案，并基于特定原因选了其中之一

缺任意一条都跳过 ADR。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
