# 深化模块（Deepening）

如何在给定依赖关系的前提下，安全地把一组浅模块合并深化。本文沿用 [SKILL.md](SKILL.md) 的词汇：**module（模块）**、**interface（接口）**、**seam（接缝）**、**adapter（适配器）**。

## 依赖分类

评估一个深化候选对象时，先对它的依赖分类。依赖类别决定了深化后的模块如何跨越其接缝进行测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。始终可深化：直接合并这些模块，并通过新接口直接测试。无需适配器。

### 2. 本地可替换（Local-substitutable）

拥有本地测试替身的依赖（例如用 PGLite 替代 Postgres，或内存文件系统）。只要存在替身即可深化。深化后的模块在测试套件中配合该替身运行。接缝位于内部；模块对外接口不需要端口（port）。

### 3. 远端但自有（端口与适配器 / Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深度模块拥有核心业务逻辑；传输层作为**适配器**注入。测试使用内存适配器，生产环境使用 HTTP/gRPC/队列适配器。

建议表述形态：*“在接缝处定义端口，为生产实现 HTTP 适配器、为测试实现内存适配器，使业务逻辑集中于同一个深度模块中，哪怕它在部署上跨越了网络。”*

### 4. 真实外部依赖（Mock）

不受你控制的第三方服务（Stripe、Twilio 等）。深化后的模块将该外部依赖作为注入的端口接收；测试提供 mock 适配器。

## 接缝纪律

- **只有一个适配器说明接缝只是假想；两个适配器才说明它是真实接缝。** 除非至少有两个合理适配器（通常是生产 + 测试），否则不要引入端口。只有单一适配器的接缝只是多余的间接层。
- **内部接缝 vs 外部接缝。** 深度模块可以拥有内部接缝（对其实现私有，供自身测试使用），同时在接口处拥有外部接缝。不要仅仅因为测试用到了内部接缝，就把它暴露到对外接口上。

## 测试策略：替换，而非叠床架屋

- 一旦在深化模块的接口层建立了测试，原本针对浅模块的旧单元测试就成了冗余垃圾；删掉它们。
- 在深化模块的接口处编写新测试。**接口即测试面（The interface is the test surface）。**
- 测试断言通过接口观察到的结果，而不是内部状态。
- 测试应当能在内部重构后依然存活，因为它们描述的是行为而不是实现。如果改了实现就必须改测试，说明测试穿透了接口。
