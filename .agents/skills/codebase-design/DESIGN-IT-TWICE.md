# 设计两次（Design It Twice）

当用户希望为选定的深化候选对象探索替代接口方案时，使用这套并行 sub-agent 模式。源自“设计两次”（Ousterhout）：你的第一个想法不太可能是最好的那个。

沿用 [SKILL.md](SKILL.md) 的词汇：**module（模块）**、**interface（接口）**、**seam（接缝）**、**adapter（适配器）**、**leverage（杠杆）**。

## 流程

### 1. 界定问题空间

在拉起 sub-agent 之前，先面向用户写出所选候选对象的问题空间说明：

- 任何新接口都必须满足的约束条件
- 它依赖哪些外部项，各自属于哪一类依赖（参见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意性代码草图，用来把约束具象化——不是最终提案，只是让约束落地

向用户展示这部分内容后，立即进入第 2 步。用户在 sub-agent 并行工作期间可以同步阅读和思考。

### 2. 并行拉起 sub-agent

并行拉起 3 个以上 sub-agent，每个都使用全新上下文窗口。每个 sub-agent 必须为深化后的模块产出一套**截然不同**的接口设计。

给每个 sub-agent 提供独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后隐藏的内容）。该简报独立于第 1 步面向用户的问题空间说明。为每个 Agent 分配不同的设计约束：

- Agent 1：“极简化接口：目标最多 1–3 个入口点，最大化每个入口点的杠杆率。”
- Agent 2：“最大化灵活性：支持多种用例与扩展方式。”
- Agent 3：“面向最常见调用方优化：让默认用法极其简单。”
- Agent 4（如适用）：“围绕端口与适配器设计跨接缝依赖。”

简报中同时纳入 [SKILL.md](SKILL.md) 的架构词汇与 `GLOSSARY.md` 的领域词汇，使每个 sub-agent 的命名既符合架构语言，又符合项目领域语言。

每个 sub-agent 输出：

1. 接口定义（类型、方法、参数，以及不变量、调用顺序约束、错误模式）
2. 展示调用方如何使用的示例代码
3. 实现隐藏在接缝背后的内容
4. 依赖策略与适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡取舍：哪些地方杠杆高、哪些地方偏薄

### 3. 逐一呈现并对比

依次呈现各套设计以便用户逐一消化，然后用散文体进行横向对比。重点对比**深度**（接口处的杠杆率）、**局部性**（改动集中在何处）以及**接缝放置位置**。

对比之后给出你自己的明确推荐：你认为哪套方案最强、为什么。如果不同方案中的优秀元素可以组合，提出一个混合方案。给出鲜明立场：用户要的是有主见的专业判断，而不是一张平铺直叙的菜单。
